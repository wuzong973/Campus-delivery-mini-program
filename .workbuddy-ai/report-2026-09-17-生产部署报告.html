部署前的一次关键拦截

⚠ 线上 app.js 含有仓库里没有的 WebSocket 功能

按惯例「上传前先比对远端与本地基线」时发现，src/app.js 与 git 仓库的版本**并不一致**：

const http = require("http");
const WebSocket = require("ws");

const app = express();
const server = http.createServer(app);        ← 线上独有
const wss = new WebSocket.Server({ server });  ← 线上独有
wss.on("connection", ...)                      ← 线上独有

module.exports = server;                       ← 导出 http.Server 而非 app

这意味着：如果按原计划直接覆盖上传，线上实时消息推送功能会当场消失， 而且不会有任何报错 —— 替换后的代码本身是合法可运行的，只是少了一整块功能。 同时 src/server.js 依赖导出的是 http.Server， 改成导出 express app 也会连带出问题。

处理方式：把 WebSocket 段完整合并进安全加固版本，保留 http.createServer 与 module.exports = server； 并把 ws: ^8.20.0 补进 server/package.json， 使本地仓库与生产环境保持一致。合并后本地跑加载测试，确认导出类型正确才上传。

⚠ 线上 env.js 把微信 AppSecret 硬编码成了兜底值

线上 src/config/env.js 里 WECHAT_APP_SECRET 有一份写死在代码中的默认值，与仓库版本不同。已确认线上 .env 中该变量配置正确， 因此移除这个兜底是安全的。

建议：该密钥长期以明文存在于服务器代码文件中（且可能在备份、快照中留痕）， 建议按「已泄露」处理并轮换。具体值未记录在任何报告或脚本中。

2. 建议轮换两个密钥

  • JWT_SECRET —— 若此前的 .env 曾随小程序代码包分发过

轮换 JWT_SECRET 会让现有用户的登录态失效（需重新登录一次）， 建议在低峰期操作。

3. 两项日志/安全优化 —— 已完成（第二批部署）

① 业务错误的 HTTP 状态码与日志分级

排查日志噪音时发现根因比预想的更深：服务层共 87 处 throw new Error(...)， 而错误中间件对没有 statusCode 的错误一律按 500 处理 —— 于是「余额不足」「请填写收件人姓名」这类正常业务结果全部变成 500 并打全量堆栈， 真正的服务异常反而被淹没。

处理方式：新增 businessError() 辅助函数，按业务语义推断状态码 （含「请重新登录」→ 401、「无权/仅…可」→ 403、「不存在」→ 404，其余 → 400）， 并对 6 个服务文件做了机械转换。配置缺失、网络失败、数据库异常等**非业务**错误 继续用 new Error 保持 500 语义，便于监控区分。

错误中间件同时改为分级日志：5xx 记录完整堆栈，4xx 只记一行摘要。

实测效果（重启后触发一次业务错误）：

# 现在（正确）
[client-error] 400 POST /api/auth/login - 缺少微信登录 code (MISSING_LOGIN_CREDENTIALS)

# 之前（错误）—— 同一个错误会打成
[server-error] { message: '缺少微信登录 code', statusCode: 500, stack: 'Error: ...' }

② nginx 移除已废弃的 TLSv1.1

ssl_protocols 从 TLSv1.1 TLSv1.2 TLSv1.3 收紧为 TLSv1.2 TLSv1.3。实测：TLS 1.1 握手被服务器拒绝，1.2 / 1.3 正常。

③ 顺带理顺 .env 的 NODE_ENV： 改为 production，与 PM2 的 ecosystem.config.js 保持一致， 避免后续维护时产生「文件里写的是 development」的误解。
