## 第五轮：第二批部署（日志分级 + TLS 收紧 + NODE_ENV 理顺）

### 挖到的更深一层根因
线上日志被「可提现余额不足」这类正常提示刷满，表面看是日志格式问题，
实际根因是：服务层共 **87 处 `throw new Error(...)`**，而错误中间件对没有 `statusCode`
的错误一律按 **500** 处理 —— 正常业务结果全变成「服务端故障」并打全量堆栈。

处理：
- 在 `shared.js` 新增 **`businessError(message, code)`**，用 `BUSINESS_STATUS_RULES`
  按业务语义推断状态码（请重新登录→401 / 无权·仅…可→403 / 不存在→404 / 其余→400）。
  匹配的是**本仓库自己写的中文提示**，不是第三方文本，因此不存在「上游改文案就失效」的问题；
  万一没命中，兜底 400 也比 500 合理。
- 对 6 个服务文件做**机械转换**：`throw new Error(` → `throw businessError(`，共 87 处
  （shared 16 / orderService 35 / paymentService 18 / userService 6 / walletService 4 /
  adminService 4 / routes/api.js 4）。
- **刻意保留为 500 的**：`config/env.js` 的 JWT 密钥校验、`api.js` 的「JWT 生成异常」、
  `subscribeMessage.js`（未被引用的参考模块，含配置缺失与网络失败）。
- `error.js` 改为分级日志：5xx 打完整堆栈，4xx 只打一行
  `[client-error] 400 POST /path - message (code)`。

### 一个被自己纠正的误判
第一次用 `openssl s_client -tls1_1` 检测 TLS 1.1 是否禁用，得到「仍可用」的错误结论。
实际是**本地 OpenSSL 3.x 默认禁用了 TLS 1.1 客户端**（`no protocols available`，
握手根本没发生，输出的 `Cipher is (NONE)` 被我的 grep 误判成成功）。
正确做法是加 `-cipher 'ALL:@SECLEVEL=0'` 降低客户端安全等级后再测：
TLS 1.1 → 已禁用，1.2/1.3 → 正常。**教训：验证「某能力是否被关闭」时，
先确认测试工具本身没有把该能力关掉。**
