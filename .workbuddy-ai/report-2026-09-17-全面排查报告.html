校园代拿小程序 · 全面问题排查报告

范围：小程序前端（pages / utils / app.*）+ 服务端（server/src）+ 部署配置 · 2026-09-17
P0 致命 · 6 项 P1 严重 · 6 项 P2 中等 · 8 项 P3 轻微 · 8 项
⚠ 最危险的一条攻击链
① 访问 GET /api/tasks（接单大厅，任意登录用户可访问）
   → 响应里 publisher 对象带出了每个发布者的 openid
② 拿任意 openid 直接 POST /api/auth/login {"openid":"..."}
   → 服务端跳过微信校验，直接签发该用户的 JWT
③ 用该 JWT 调用任意接口 → 接管任意账号
④ 若列表中含管理员 openid → 接管后台，可审批/驳回全部提现
下面 P0-1 与 P0-2 单独看都是弱点，组合起来就是一条完整的、无需任何前置条件的账号接管链。

P0 · 致命（必须立即修复）

可在无授权情况下造成资金损失、数据泄露或服务沦陷
1登录接口接受任意 openid，完全跳过微信校验
安全资金
具体表现
server/src/services/authService.js:69-82 —— const directOpenid = String(payload.openid||"").trim()；只要请求体带 openid，就不再调用 codeToSession() 做微信侧校验，直接为该 openid 建号/签发 token。
客户端 utils/auth.js:99-124 正是走这条路径做「会话恢复」——说明它就在正常业务主链路上，不是废弃代码。
影响范围
全站任意账号接管。结合 P0-2 的 openid 泄露，攻击者无需任何密钥即可登录他人账号、查看订单与聊天、发起提现。
排查方向
确认生产是否必须保留 directOpenid 通道；若保留，改为校验已有会话签名（如用服务端密钥对 openid 签发短期 ticket），而不是裸传 openid。同时检查网关是否能限制该字段。
2openid 在公开接口中全量泄露
安全
具体表现
shared.js 的 normalizeUser() 无条件返回 openid；而 enrichOrder() 把 publisher / runner 原样塞进响应。
formatChatSession() 的 currentUser / targetUser 同样如此。
于是 GET /api/tasks（接单大厅，任何登录用户可访问）会返回每个发布者的 openid。
影响范围
为 P0-1 提供弹药，构成完整接管链。管理员若发过单，其 openid 也在此列表中 → 后台沦陷。
排查方向
给 normalizeUser 增加一个 publicUser() 变体，只输出 id / nickname / avatarUrl / avatarTheme / avatarText / completedJobs / averageScore；对外接口一律改用该变体。全仓搜索 normalizeUser( 逐个确认。
3JWT 密钥存在硬编码兜底值，且 role 直接采信 token
安全
具体表现
server/src/config/env.js:45-48 —— jwtSecret: trimValue(process.env.JWT_SECRET, "campus-runner-dev-secret")。生产若漏配环境变量，退化为一个公开可知的字符串。
server/src/middleware/auth.js:22 —— 建号时 role: decoded.role || "user"，把 token 里的角色声明当真。
影响范围
攻击者可用已知密钥自签 {openid:任意, role:"admin"} 的 token → 直接获得管理员权限，可审批/驳回全部提现、查看全部用户与订单。
排查方向
① 生产环境注入 JWT_SECRET 并改为缺失即启动失败（不要有兜底）；② 建号时 role 固定为 "user"，管理员只能由 ADMIN_OPENIDS 白名单或数据库手动授予。
4.env 位于小程序根目录，会被打进代码包
安全
具体表现
根目录存在 .env，含 JWT_SECRET、WECHAT_APP_SECRET、MONGODB_URI、ADMIN_OPENIDS、WECHAT_PAY_*。已确认键名清单，未打印任何值。
project.config.json:5 miniprogramRoot: "./"，且 packOptions.ignore: [] 未排除任何内容。
影响范围
小程序代码包可被反编译，密钥、数据库地址、管理员白名单一次性泄露。
排查方向
把 .env 与 server/、cloudfunctions/ 加入 packOptions.ignore；更彻底的做法是把小程序源码拆到 miniprogram/ 子目录并调整 miniprogramRoot。同时确认已泄露的密钥是否需要轮换。
5订单结算非幂等，并发完成会重复打款
资金逻辑
具体表现
settleOrderIfNeeded() 是典型的「先查后写」：先 SettlementLog.findById(order._id) 判断是否已结算，然后 $inc 骑手 walletBalance / totalIncome / completedJobs，最后才 upsert 结算日志。
orderService.js:429-456 completeOrder() 同样是先 findById 判状态、再执行结算，无事务包裹。
影响范围
两个并发的「确认完成」请求（用户连点、网络重试、前后端重试）都会通过前置检查 → 骑手余额被 $inc 两次，平台真实资金损失。订单量越大、网络越差越容易触发。
排查方向
把 upsert 前置并作为唯一闸门：SettlementLog.findOneAndUpdate({_id, status:{$ne:"settled"}}, {$set:{status:"settling",...}}, {upsert:true,new:true})，只有抢到这条记录的请求才继续 $inc；或直接引入 MongoDB 事务 / 用 payStatus+status 做条件 update 并校验 modifiedCount。排查时可用并发脚本重复调用 /orders/:id/complete 复现。
6取消订单无并发保护，存在重复退款风险
资金
具体表现
orderService.js:470-513 cancelOrder() 先读订单判状态 → 调 applyRefund() → 最后才 update 状态。applyRefund() 内部虽有二次刷新，但两个并发请求仍可能读到同一份 pre-state。
全流程无幂等键、无锁、无事务。
影响范围
同一订单被重复退款，资金双向损失（用户多收、平台多付）。
排查方向
用条件 update 抢占状态（{_id, status:{$in:["pending","accepted"]}} 并校验 modifiedCount===1），只有抢占成功者才继续退款；退款侧以 outRefundNo 做幂等，先查后发。

P1 · 严重（本周内修复）

会造成错误结果、明显性能退化，或显著扩大攻击面
7上传文件扩展名未白名单，可写入任意后缀
安全
具体表现
server/src/routes/api.js:78-80 const ext = path.extname(file.originalname || "") || ".jpg" —— originalname 完全由客户端控制。
唯一的 imageFileFilter 只校验 mimetype，同样是客户端可控字段。
影响范围
伪造 Content-Type: image/png + 文件名 x.php 即可落盘 .php。当前 deploy/nginx/wzl136122.cn.conf 的 location ^~ /uploads/ 是纯静态 alias，侥幸阻止了执行——但这属于单点依赖，换环境或改配置即 RCE。
另外 image/svg+xml 可直接通过过滤，同源静态服务未设 X-Content-Type-Options: nosniff 与 CSP → 存储型 XSS。
排查方向
改为服务端白名单 ['.jpg','.jpeg','.png','.webp'] 强制重写扩展名，并用文件魔数（magic bytes）校验真实类型；/uploads/ 响应加 X-Content-Type-Options: nosniff、Content-Security-Policy: default-src 'none'。
8接单竞争未校验修改结果，失败方误报「接单成功」
逻辑
具体表现
orderService.js:352-363 的 updateOne({_id, status:"pending", payStatus:"paid"}, ...) 条件本身是原子的，但代码没有检查 modifiedCount，后续照常发通知、返回详情。
影响范围
两名骑手同时点击接单：都通过前置校验，只有一条 update 真正命中；未命中方前端仍 toast「接单成功」，但实际未获得订单，且发布者收到两条接单通知。造成纠纷与信任问题。
排查方向
取 updateOne 返回值，modifiedCount !== 1 时抛「订单已被其他同学接走」。
9个人敏感字段全量下发（手机号 / 常用地址）
安全
具体表现
normalizeUser() 无条件返回 phone、commonAddress、openid、walletBalance、totalIncome。
接单大厅把每个发布者的真实手机号与常用地址发给所有登录用户——而前端只用到 publisher.nickname。
影响范围
大规模个人信息泄露，违反《个人信息保护法》最小必要原则；可能被用于骚扰、社工。
排查方向
与 P0-2 一并处理：对外只输出展示必需字段。注意订单的 contactPhone 已有 canViewContact 保护，说明作者有脱敏意识，只是 normalizeUser 这条路径漏了。
10CORS 全开 + 无限流 + 无安全响应头
安全
具体表现
server/src/app.js:12 app.use(cors()) 未限定 origin、未限制 method。
全站无 rate limit；无 helmet；nginx 未设 X-Content-Type-Options / X-Frame-Options / CSP。
影响范围
/auth/login 可撞库；下单、提现、发消息可脚本刷量；恶意站点可诱导已登录用户发起跨站请求。
排查方向
cors({origin: 白名单})；对 /auth/login、/orders、/wallet/withdrawals、聊天发送加 express-rate-limit；补 helmet() 与 nginx 安全头。
11聊天详情每 4 秒触发一次「历史数据迁移」全表查询
性能
具体表现
pages/chat/detail/detail.js:3 POLL_INTERVAL_MS = 4000。
每次轮询 → getChatMessages() → bindLegacyMessagesToSession()，后者执行 Chat.find({sessionId:{$exists:false/"" /null}, ...}) 的 $and+$or 复合查询。
影响范围
这是一次性数据迁移逻辑，却常驻在 4 秒一次的热路径上。随 chats 集合增长，该查询会持续拖慢数据库；同时每次轮询还无条件执行 Chat.updateMany + ChatSession.updateOne 两次写操作，即使一条新消息都没有。
排查方向
把迁移逻辑拆成一次性脚本（或在会话创建时执行一次并打标记）；轮询接口改为只读，仅在确实有新消息时才写。
12同一接口被三重定时器叠加轮询
性能
具体表现
app.js:71 全局 15s 轮询 /chat/sessions；pages/chat/chat.js:3 聊天列表 5s 轮询同一接口；pages/chat/detail/detail.js:3 聊天详情 4s 轮询消息。
影响范围
进入聊天页时两个定时器同时对 /chat/sessions 发请求，请求量翻倍。更糟的是 chat.js 的 catch 每 5 秒弹一次 toast —— 断网时会连续刷屏无法操作。
排查方向
统一到一个全局轮询源（页面进入时暂停 app 级轮询）；失败时静默退避，不在轮询里弹 toast。
13主包体积必然超限，无法上传发布
兼容性能
具体表现
miniprogramRoot: "./" 导致 cloudfunctions/（68M）、server/（21M）、server.zip（4.9M）、.env 全部被纳入小程序包。
packOptions.ignore: [] 未排除任何目录；cloudfunctionRoot: "" 也未按云函数目录特殊处理。
小程序真正需要的只有 pages/ + utils/ + app.*，实测约 377K。
影响范围
主包上限 2MB。当前配置下预览/真机编译极慢，上传大概率直接失败。
排查方向
在 packOptions.ignore 中排除 server/**、cloudfunctions/**、server.zip、.env、*.md；或将小程序源码移入独立子目录。

P2 · 中等（排期修复）

影响稳定性、健壮性或体验，在特定条件下触发

异常
表现：pages/chat/detail/detail.js:345-359 uploadChatImage().then(...).finally(...)，中间没有 catch。
影响：上传失败产生未捕获 Promise rejection，用户只看到 loading 消失，无任何提示，且 uploadingImage 状态靠 finally 复位但错误被吞。

15关键资金操作缺防连点锁
逻辑资金
表现：taskDetail.js:322 handlePay、:414 handleComplete、:458 submitRating 均没有 submitting 锁；而同文件的 handleAccept:225、handleCancel:281 有。
影响：连点会并发发起支付、重复结算、重复评价。与 P0-5 叠加时正是重复打款的触发条件。

16全站无分页，无 onReachBottom
性能
表现：全仓搜不到 onReachBottom。getTaskList 硬编码 .limit(50)，getOrderList 返回全量，admin 一次返回 30 用户 + 40 订单。
影响：订单页一次性 setData({rawList}) 全量订单，数据增长后逼近 setData 1MB 上限并显著拖慢渲染。
方向：订单/任务/后台列表改分页 + 上拉加载。
17多个页面在 onShow 发全量请求
性能
表现：index / order / mine / publish / wallet / admin 均在 onShow 触发完整网络往返 + 全量 setData；mine.js 还叠加启动通知监听。
影响：每次切 tab 都卡顿一下，弱网下尤其明显。
方向：加「距上次刷新 N 秒内不重复请求」的节流，或改为增量拉取。
18taskList.js 缺空值兜底，与 order.js 不一致
异常
表现：loadTasks 中 data.list.reduce(...) 与 rawList: data.list 直接信任后端返回的 list；而 order.js 对应位置有 || [] 保护。
影响：后端异常未返回 list 时抛 TypeError，页面白屏且无提示。
方向：统一加 (data && data.list) || []。
19提现金额前端校验不严
逻辑
表现：wallet.js if (!amount || Number(amount) <= 0) —— 输入 "abc" 时 NaN <= 0 为 false，直接绕过前端校验；也未校验两位小数与余额上限。
影响：后端 roundMoney 会拦截，但用户得不到即时反馈，体验割裂。
方向：改用 Number.isFinite() 判断，并校验小数位与可提现余额。
20NoSQL 操作符注入面
安全
表现：ChatSession 更新用 unreadCounts.${currentOpenid} 把 openid 直接拼进 update 路径（shared.js getChatMessages 中）。
影响：openid 可经 P0-1 的 directOpenid 通道由外部控制，且未做字符白名单校验，含 . 或 $ 的取值可能改变更新路径语义。
方向：对 openid 做 /^[A-Za-z0-9_-]{1,64}$/ 校验；或把 unreadCounts 改为数组/子文档避免动态键。
21错误中间件在 development 下回传堆栈
安全
表现：server/src/middleware/error.js:32-34 NODE_ENV === "development" 时响应体包含 stack 与 detail。
影响：生产若误配 NODE_ENV，会泄露服务器绝对路径与代码结构，辅助攻击者构造利用。
方向：改为显式白名单（如 DEBUG_ERRORS === "1"），且堆栈只写日志不回传。
