1登录接口接受任意 openid，完全跳过微信校验
修复方式

客户端同步改造
utils/auth.js 重构为三条清晰路径： loginWithWechatCode()（唯一合法登入方式）、 restoreSession()（用已有 token 校验，带 skipAuthRetry 防止 request 层再触发一次登录）、 runLogin()（并发去重）。 app.js 启动改为 auth.ensureLogin()，不再传递缓存的 openid。
2openid / 手机号 / 常用地址在公开接口中泄露
修复方式
server/src/services/shared.js 新增 publicUser()： 只输出 id / nickname / avatarUrl / avatarTheme / avatarText / slogan / completedJobs / averageScore / ratingText， 不含 openid、手机号、常用地址与钱包收益。
三处对外下发他人信息的地方全部改用它： enrichOrder() 的 publisher 与 runner、 formatChatSession() 的 targetUser 与 currentUser。
normalizeUser() 保留给「本人」场景（/users/me、/mine）。
效果
接单大厅不再向所有登录用户广播每个发布者的手机号、常用地址与 openid，P0-1 的攻击链失去弹药。

5订单结算非幂等，并发完成会重复打款
修复方式（两层防护）
第一层：orderService.js completeOrder() 用条件 update {_id, runnerOpenId, status:"delivered"} 原子抢占，并校验 modifiedCount， 只有抢到的请求才发通知。
第二层：shared.js settleOrderIfNeeded() 以 SettlementLog.status 作为唯一闸门做原子抢占。 用 findOneAndUpdate(new:false) 读取更新前的文档判断归属： null = 本次抢到、settled = 已结算直接返回、 settling = 另有请求在结算，跳过不动钱。 并设 5 分钟 stale 超时，进程崩溃后可补偿结算，不会让订单永远结不了账。
upsertFinanceStats() 同步改为单次原子 $inc + upsert， 消除「先查是否存在再 create」的并发重复累加与 _id 冲突。
6取消订单无并发保护，可能重复退款
修复方式
orderService.js cancelOrder() 先原子抢占订单状态 （{_id, status:{$in:["pending","accepted"]}} → cancelled， 校验 modifiedCount === 1），只有抢占成功者才发起退款。
新增退款失败回滚：若 applyRefund 抛错，把订单状态恢复为原值并清空 cancelledAt，避免出现「已取消但没退款」的悬空状态，用户可重新发起取消。

P1 · 严重问题（7 项，全部修复）

7上传文件扩展名未白名单（可写 .php / 传 SVG）
修复方式（三层）
扩展名由服务端决定：routes/api.js 用 MIME_EXT_MAP 把 mimetype 映射到固定安全扩展名，不再使用客户端的 originalname。
内容校验：新增 verifyUploadedImage 中间件，落盘后读取文件头 校验魔数（JPEG / PNG / GIF / WEBP），不匹配立即 unlink 并返回 400。 mimetype 与文件名都能伪造，只有文件内容伪造不到能通过魔数校验的程度。
nginx 兜底：deploy/nginx/wzl136122.cn.conf 为 /uploads/ 补 X-Content-Type-Options: nosniff、Content-Security-Policy: default-src 'none'; sandbox， 并对 .php/.phtml/.jsp/.sh/.py 等后缀 deny all。
附带加固
文件名随机部分从 Math.random().toString(16).slice(2,8) 改为 crypto.randomBytes(12).toString("hex") —— 上传目录是公开静态可访问的，文件名是唯一访问凭据，必须不可枚举。
8接单竞争未校验结果，失败方误报「接单成功」
修复方式
acceptTask() 取 updateOne 的返回值， modifiedCount !== 1 时抛「手慢了，该订单已被其他同学接走」。 发布者也不会再收到两条重复的接单通知。
9个人敏感字段全量下发
与 P0-2 同一处修复：publicUser() 统一收敛对外字段， 接单大厅不再返回发布者的真实手机号与常用地址。
10CORS 全开 + 无限流 + 无安全头
修复方式（零新增依赖）
考虑到生产服务器重新 npm install 常受网络与权限限制， 自行实现 server/src/middleware/security.js： securityHeaders（nosniff / X-Frame-Options / Referrer-Policy / 移除 X-Powered-By）、 createRateLimiter（内存滑动窗口，带自动回收与标准 RateLimit 响应头）、 createCorsOriginChecker（小程序请求不带 Origin 故放行，浏览器跨域只认白名单）。
app.set("trust proxy", 1)，使 nginx 之后能取到真实客户端 IP， 否则限流会把所有请求算到 nginx 地址上。
分层限流：全站 300/分钟，登录 20/5分钟，下单 20/10分钟，提现 5/10分钟，发消息 60/分钟。
新增 CORS_ORIGINS 环境变量（留空即不放行任何浏览器跨域请求）。
11聊天详情每 4 秒触发一次历史数据迁移全表查询
修复方式
排查时发现 ensureChatSession() 本来就调用过 bindLegacyMessagesToSession()，getChatMessages() 里那次是纯重复。 现在只在「会话从未有过任何消息」（!session.lastMessageAt，纯内存判断，无额外查询） 时兜底执行一次。
同时把 Chat.updateMany + ChatSession.updateOne 两次写操作 改为仅当 unreadCounts[currentOpenid] > 0 时才执行 —— 轮询在没有新消息时保持纯读。
12同一接口被三重定时器叠加轮询
修复方式
app.js 的全局轮询在检测到当前页面是聊天列表页时直接跳过 （通过 getCurrentPages() 判断 route），消除对 /chat/sessions 的双重轮询。
chat.js 与 detail.js 从固定 setInterval 改为自调度 setTimeout，支持指数退避 （连续失败时 5s → 10s → 20s → 40s，上限 60s），断网时不再持续高频请求。
轮询失败改为静默（console.warn），只有首次加载和用户主动下拉才弹提示 —— 旧实现每 5 秒弹一次 toast，断网时会把屏幕刷满、用户完全无法操作。

排查中发现并修复的两个额外问题

A · .env 反向覆盖真实环境变量（部署陷阱）
问题
server/src/config/env.js 原本使用 dotenv.config({ override: true })，意味着 .env 文件会覆盖真实环境变量。 运维即便在 systemd / Docker 里显式设置了 NODE_ENV=production， 也会被文件里的 development 悄悄改回去 —— 直接导致生产以开发模式运行，并绕过 JWT_SECRET 的强制校验。
修复
改为 override: false，真实环境变量优先（符合 12-factor 原则）。
验证
已实测：设置 NODE_ENV=production JWT_SECRET=... 后， nodeEnv 正确读为 production，密钥取自环境变量而非文件。
B · $set 中包含不可变的 _id（修复过程中自查发现）
问题
重写结算逻辑时，收尾更新误把 _id 放进了 $set。 MongoDB 不允许修改 _id，会直接报 "Performing an update on the path '_id' would modify the immutable field '_id'"， 导致结算永远失败。
修复
抽出 settlementFields（不含 _id）， _id 只出现在查询条件里；同时避免 $set 与 $setOnInsert 字段重叠。
